1. The problem — start here, not with code

Unplanned hydraulic failures stop production lines. A failed cooler or a leaking pump doesn't just cost a spare part — it costs the unplanned shutdown, the rush technician visit, and the production that didn't happen.

But most ML tutorials miss the point: "something is wrong" is not an actionable prediction. A maintenance planner needs three answers:

  1. Which component is degrading — cooler, valve, pump, or accumulator?
  2. How badly — full efficiency, reduced, or close to failure?
  3. What should I do about it — and when?

This project answers the first two. (The third becomes Project #3 in my portfolio: a maintenance decision engine.)

Product lensAnyone can train a classifier. A product person starts from the decision the prediction enables. That framing is what this whole project is built on.

2. The data

The dataset comes from a hydraulic test rig at a research lab, published by Helwig et al. to the UCI Machine Learning Repository (2018). It holds 2,205 operating cycles, each 60 seconds long, recorded under systematically varied component health states. Because fault states were induced deliberately, the labels are trustworthy — the closest public analog to labeled industrial asset data, which is notoriously hard to get.

3. EDA: do the signals separate the faults?

The single most important EDA question: if I plot the average sensor trace per fault class, do the curves separate? If yes, a classifier has something real to learn. If no, stop.

Class distributions

The physics check

I tested two physical hypotheses against the raw signals:

  • Hypothesis A: a degraded cooler can't reject heat → oil temperature sensors (TS3/TS4) should run hotter as cooler condition worsens.
  • Hypothesis B: a lagging valve changes switching dynamics → pressure sensors (PS1/PS2) should show reshaped plateaus.
What this chart is forHypothesis A confirmed, dramatically: a cooler "close to failure" runs at ~56°C vs ~39°C at full efficiency — a ~17°C separation visible to the naked eye. Hypothesis B confirmed: valve lag visibly reshapes pressure plateaus. Before showing any model score, I can show a plant manager this image and say: "Your sensors already see the failure coming. We're just teaching a computer to watch them 24/7." That sentence is worth more than any F1 score in a stakeholder meeting.

4. Feature engineering: 43,680 numbers → 187 features

43,680 values per cycle can't go into a classifier directly. The standard, honest baseline for this benchmark: compress each cycle into statistical descriptors — transparent, explainable, and fast.

The 11 features per sensor (each explainable in one sentence)

FeaturePhysical meaning
meanOperating level (e.g. steady oil temperature)
stdFluctuation around the level
min / max / medianExtremes; median is the spike-robust level
ptpPeak-to-peak swing
rms / energySignal energy level
crestPeak ÷ RMS — spikiness: transients and impacts
skewAsymmetry — e.g. one-sided pressure spikes
kurtTailedness — impulsive events

17 sensors × 11 features = 187 features per cycle. The implementation (src/data.py:build_feature_frame()) processes sensors one file at a time — the raw files total ~500 MB, and the boring engineering detail of not blowing memory is exactly what interviewers like to hear.

def signal_features(x):
    x = np.asarray(x, dtype=float)
    rms = np.sqrt(np.mean(x ** 2))
    return {"mean": np.mean(x), "std": np.std(x),
            "min": np.min(x), "max": np.max(x),
            "median": np.median(x), "ptp": np.ptp(x),
            "rms": rms, "crest": np.max(np.abs(x)) / (rms + 1e-12),
            "skew": stats.skew(x), "kurt": stats.kurtosis(x),
            "energy": np.mean(x ** 2)}

5. Modeling: four small problems, not one big one

Decision 1 — one classifier per component

The rig varies components independently, so failure modes are independent. Four focused models are simpler to debug and map 1:1 to work orders ("the cooler needs attention"). When the problem decomposes naturally, decompose the model too.

Decision 2 — RandomForest vs HistGradientBoosting, winner per component

Tree ensembles: no normalization needed, robust to correlated features, and they give feature importances for free.

for t in TARGETS:  # cooler, valve, pump, accumulator
    X_train, X_test, y_train, y_test = train_test_split(
        X, y[t].values, test_size=0.2, random_state=42,
        stratify=y[t].values)          # every fault state in both sets
    for name, model in [("rf", RandomForestClassifier(
                                n_estimators=300, n_jobs=-1, random_state=42)),
                        ("hgb", HistGradientBoostingClassifier(random_state=42))]:
        model.fit(X_train, y_train)
        pred = model.predict(X_test)

Decision 3 — no leakage, by construction

Discipline that mattersFeatures are computed per cycle and the split is by cycle (stratified 80/20, seed 42). No cycle appears in both sets. Leakage through overlapping time windows is the #1 silent killer of time-series ML credibility — stating the discipline explicitly is what separates a careful practitioner from a notebook hobbyist.

Honest readThese are strong — almost suspiciously strong. The truth: test-rig data with deliberately induced, well-separated faults is the easy case. Real plants add drift, dropouts, and mixed modes. I volunteer that before being asked — it builds more credibility than perfect scores do.

Reading these as a maintenance planner

  • Cooler: clean diagonal — a "reduced efficiency" flag is trustworthy enough to schedule service, not just investigate.
  • Valve / accumulator: rare confusions sit between adjacent severity states — the good kind of error. The action (inspect the valve) is the same either way.
  • The expensive error — predicting "healthy" when truth is "close to failure" — is essentially empty across all four matrices. That's the cell that prevents unplanned shutdowns, and it's what I'd monitor in production.

The product insightThis chart answers a budget question, not a modeling question. If temperature sensors dominate cooler prediction, a plant can retrofit just those and skip the expensive 100 Hz pressure array. ML tells you what to predict; feature importance tells you what to buy. That's the sentence I'd use with a VP of Operations.

8. Limitations — stated before anyone asks

  1. Test rig ≠ plant floor. Next: robustness tests with synthetic sensor noise and missing-data regimes.
  2. Single split, single seed. Next: repeated stratified CV with confidence intervals.
  3. Fixed 60-second framing. A streaming deployment needs windowing, latency budgets, and alert debouncing — otherwise you page someone 60 times for one degrading cooler.
  4. No spectral features yet. The 100 Hz pressure/power signals deserve FFT-band features.
  5. No sequence-model challenger. A 1D-CNN/LSTM on raw signals is the natural next comparison.

9. From model to product

A model in a notebook saves nobody money. Here's the productization path — and how I'd discuss it in a Director/Head/AI-Lead interview:

  • Users & decisions: reliability engineers and maintenance planners. Output must land in the existing CMMS/work-order flow — not another dashboard nobody opens.
  • KPIs that matter: not F1 — unplanned downtime hours avoided, false-alarm rate per 100 cycles (alert fatigue kills adoption), mean lead time (cycles of warning before "close to failure").
  • Rollout: shadow mode beside human planners for 4–6 weeks → "recommend" → auto-raise low-risk work orders. Trust is deployed in stages.
  • The cost layer (→ Project #3): P(failure) × cost of unplanned downtime vs cost of planned intervention turns "pump: weak leakage" into repair now / inspect later / continue. That's where the MBA meets the ML.

10. Interview prep: questions I'd expect

Q: Why one model per component instead of multi-output?

A: Components degrade independently, so failure modes are independent. Separate models debug cleanly, map 1:1 to work orders, and let me pick the best algorithm per component.

Q: Why macro-F1 instead of accuracy?

A: Accuracy lets a model hide behind the majority healthy class (valve is 51% "optimal"). Macro-F1 forces every fault state to count equally — missing a rare "close to failure" is the expensive error.

Q: How did you avoid leakage?

A: Features per cycle, split by cycle, stratified, fixed seed. With time-series I'd also watch for overlapping windows leaking across the split; here cycles are independent by construction.

Q: Why statistical features instead of deep learning?

A: It's the honest baseline — explainable to the engineers who must trust it, trains in seconds, and scores are near-ceiling. I'd still run a 1D-CNN challenger next; I list that explicitly rather than pretending the baseline is final.

Q: Cooler accuracy is 1.0 — overfitting?

A: Easy case, not overfitting: test-rig data, induced faults, 17°C naked-eye separation. I'd say this upfront — the real test is plant data with drift.

Q: How would you deploy it?

A: Shadow mode → recommend → auto-raise low-risk work orders. Instrument false-alarm rate and lead time. Feed predictions into a cost-based decision engine (my next project).

Q: What with twice the time?

A: Spectral features, sequence-model challenger, repeated CV, missing-data robustness, streaming/windowing design.
